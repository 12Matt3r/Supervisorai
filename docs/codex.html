overview

What SupervisorAI is

A supervisory reasoning engine: one agent plans a job, hands each step to a specialist, and verifies every result before it counts.

Autonomous agents fail in a specific, expensive way — they lose the plot. A coding agent drifts into rewriting unrelated files; a research agent cites a source that says the opposite of what it claims; a multi-step task reports “done” while a dependency silently failed. The missing piece is not a bigger worker model — it is a supervisor that holds the plan, checks each step against it, and refuses to declare success until the work verifies.

SupervisorAI is that supervisor. It uses MiniMax-M3 to run a closed loop over a team of workers: Plan → Delegate → Audit → Correct → (approve) → Synthesis. Every stage streams as a tagged live trace, and verified outputs are written to disk as real files — a bug fix whose generated tests actually pass against the generated code.

concept

The supervisory loop

The six-stage reasoning cycle that turns one natural-language objective into a verified result.

The loop is driven by Orchestrator.run_goal(). It is a real DAG execution, not a linear script: tasks with satisfied dependencies become eligible, run, and are audited before their dependents unlock.

01
Plan
M3 decomposes the goal into a validated task DAG, assigning a specialist and a deliverable per task.
02
Delegate
Each ready task runs on its assigned specialist persona.
03
Audit
M3 verifies every output against the plan and continuity rules.
04
Correct
Failed or drifted outputs are re-prompted with a concrete fix hint.
05
Approve
High-stakes tasks halt for human approval (HITL) before finalizing.
06
Synthesize
Once every dependency passes, M3 produces the verified final result.

Each stage emits a tagged trace line so the reasoning is legible in real time:

[SUPERVISOR - M3][DISPATCH][AUDIT][DRIFT DETECTED][RECOVERY][PASS / SYNTHESIS]

Quickstart

Configure a key and run the end-to-end demo against real MiniMax-M3.

pip install -r requirements.txt

# 2. configure GMI (never commit the key — .env is gitignored)

#    GMI_BASE_URL defaults to https://api.gmi-serving.com/v1
#    SUPERVISOR_MODEL defaults to MiniMaxAI/MiniMax-M3

# 3. run the turnkey demo (mock-repo bug fix, live trace, verified files)
python demo.py

# 4. run the test suite
PYTHONPATH=src pytest tests/ -q          # 46 passing

With no key, the client falls back to a deterministic mock so the demo, tests, and MCP server never hard-crash.

LLMClient — the M3 adapter

The single integration point: every LLM call in the system flows through this one class.

Every LLM-using component — the orchestrator’s decomposer, the LLMJudge, and the researcher’s assistor — depends on LLMClient (src/llm/client.py). Retargeting this one class flips the entire platform onto MiniMax-M3, which is exactly how the Anthropic-built system was moved to GMI Cloud.

On top of the raw endpoint it adds production concerns: retry with exponential backoff (on 429 / 5xx / network), token-budget accounting, robust structured-JSON extraction (fenced and embedded JSON), tool-calling pass-through, SSE streaming, and a context-aware mock fallback. It keeps the legacy query() contract and adds a richer complete() envelope.

component

Orchestrator

Decomposes goals into a task DAG and drives the Plan→Delegate→Audit→Correct→HITL→Synthesis loop.

Orchestrator (src/orchestrator/core.py) owns run_goal(). It asks M3 to decompose the objective (submit_goal()), then repeatedly pulls ready tasks and runs each through _run_supervised_task(): resolve the specialist persona, dispatch to an M3 worker, run the supervisor engine, run the M3 audit, correct on failure, gate high-stakes tasks through HITL, and write the verified deliverable.

A worker’s raw output is cleaned into a usable file by _extract_deliverable() — it strips markdown fences and unwraps JSON-enveloped code so .py/.html/.json land valid. Worker token budget is WORKER_MAX_TOKENS = 6000 so long files don’t truncate.

Bug fixed here: the orchestrator originally deadlocked on a non-reentrant lock (update_agent_status → get_agent re-acquired the same Lock). It now uses an RLock.

data model

Task & DAG model

The typed structures that make the plan a real dependency graph, not a to-do list.

A ProjectGoal holds a dict of OrchestrationTasks; get_ready_tasks() returns those whose dependencies are all COMPLETED. Each task carries what the loop needs to supervise it:

  • dependencies, required_capabilities — the DAG edges and routing hints
  • assigned_agent, deliverable — the specialist and target filename M3 chose
  • validation_conditions — the concrete checks the audit enforces
  • high_stakes — whether it must pass the HITL gate
  • output_text, audit, attempts, deliverable_path — the run record

component

SupervisorCore

The monitoring & intervention engine that scores an output and decides whether to step in.

SupervisorCore (src/supervisor_agent/core.py) runs monitor_agent() then validate_output(). Validation blends a heuristic quality score (60%) with the LLM judge’s second opinion (40%), analyzes coherence for drift, and asks the Expectimax agent whether to intervene. Interventions escalate through WARNING → CORRECTION → ESCALATION → ASSISTANCE; a repeated-failure “stuck” detector triggers the ResearchAssistor.

Correctness fix: when no real judge is available (unconfigured/mocked) the judge now flags llm_available:false and validation relies on the heuristic alone — blending in a fabricated 0.85 used to mask genuinely poor outputs.

See also · Expectimax · Quality & coherence · Self-correction
component

Expectimax agent

A probabilistic decision model that chooses the supervisor’s action by looking ahead.

Rather than fixed thresholds, the Expectimax agent (expectimax_agent.py, depth 2) weighs a state — quality, drift, error count, resource use — over probable future outcomes and picks an action: ALLOW, WARN, CORRECT, or ESCALATE. The action set is state-gated: quality below 0.4 removes “allow” from the table (only CORRECT/ESCALATE); quality at or above 0.9 offers only ALLOW/WARN.

Bug fixed here: the intervention map referenced Action.CORRECTION, but the enum member is Action.CORRECT — it raised on every intervention until corrected.

component

LLM judge

A second, independent M3 opinion on whether an output meets its goals.

LLMJudge (llm_judge.py) asks M3 to score an output for coherence, adherence, and safety, returning a structured verdict the supervisor blends into its quality score. When unconfigured it returns a placeholder score marked llm_available:false, so callers can choose to rely on their own heuristic instead of a fabricated opinion.

component

Quality & coherence

The heuristic analyzers that score an output’s structure and detect drift from the goal.

The QualityAnalyzer combines structure, coherence, instruction-adherence, and completeness into a single confidence score. The CoherenceAnalyzer computes a drift score — how far an output has wandered from its original goals. Together they give the supervisor a fast, offline read on quality that does not depend on a network call.

Bug fixed here: QualityMetrics was missing a completeness_score field, which crashed validate_output for everyone until added.

Agent roster

Named specialist personas; M3 assigns the right one to each task at plan time.

Worker personas live in agents/*.json — each declares a name, capabilities, and a persona system prompt. The roster (roster.py) is fed to M3 during decomposition so it can assign the best specialist per task, and each worker then runs with its persona as its system prompt.

The starter roster: analyst.strategic, coder.python, coder.javascript, coder.typescript, writer.narrative, writer.docs, researcher.web, reviewer.code. The vortex-os-v3 skill extends this to a 30+ agent software roster.

Continuity engine

Hard canon constraints — era, character, tone, safety — enforced on every task.

continuity_rules passed to run_goal() are injected into every worker prompt, folded into each audit’s validation conditions, and guarded by a fast deterministic pre-check (_continuity_violation() catches literal forbidden tokens like a “no smartphones” rule). A violation triggers the same self-healing correction path as a failed audit.

capability

Audit & verification

After every worker output, M3 puts on its supervisor hat and verifies the result against the plan.

The audit (_audit()) asks M3 for a strict JSON verdict — verdict, confidence, drift_detected, issues, correction_hint — checking the output against the task’s validation conditions plus any continuity rules. It is deliberately rigorous: in live runs it has correctly rejected a worker that fabricated “tests passed,” and caught truncated output. Only a passing, non-drifted verdict lets a deliverable be written.

This M3 audit is the authoritative verdict; the SupervisorCore heuristic + judge pass runs alongside it as a second signal.

capability

Self-correction

Failed or drifted outputs are re-prompted with a concrete fix hint until they pass.

When an audit fails, the loop feeds the verdict’s correction_hint back to the worker and retries (up to max_corrections). This is real: in live runs the reviewer step has drifted into dynamic reasoning, been caught, and passed on the corrected attempt. There is no round limit gaming — repeated failures mean the loop keeps re-prompting toward the root cause, and a task that can’t be recovered fails the plan rather than shipping.

[DRIFT DETECTED][RECOVERY][PASS]

HITL Deep-Sleep gate

High-stakes steps halt for explicit human approval before anything is finalized.

Tasks the planner marks high_stakes (finalizing or packaging a shippable artifact) pause before their deliverable is written. HITLGate (hitl.py) persists a pending-approval record to disk; a human approves or denies out-of-band via the MCP tools (hitl_status/hitl_approve/hitl_deny) or an approval callback in code. A run with no operator halts with status PENDING_APPROVAL.

The invariant is: never auto-approve. Even a blanket “do whatever you want” does not bypass the gate — it is the last line of defense against a runaway action.

capability

On-disk deliverables

Every verified output is written to deliverables/ as a real, standalone file.

Workers are told the exact target filename and asked for raw file contents. The output is cleaned — _strip_code_fence() and _extract_deliverable() unwrap prose-wrapped or JSON-enveloped code — so a .py, .html, or .json lands valid and runnable. Nothing is written until it passes audit (and HITL, when high-stakes). In a live run this produces a fix and a test file whose generated tests pass against the generated code.

MCP server

Exposes the supervisor as callable MCP tools for other agents and clients.

src/server/main.py is a FastMCP server. Alongside the monitoring and orchestration tools it exposes the studio loop and gate: run_master_goal, hitl_status, hitl_approve, hitl_deny, plus submit_goal, monitor_agent, validate_output, and the Expectimax decision tools. A high-stakes run returns PENDING_APPROVAL and the pending list, so a human can release it and resume.

VORTEX-OS — creative flavor

The same 4-tier orchestration as a command-line studio skill (implementations/vortex-os/) — a downstream client of the Python engine, not the core.

A bash “skill” that runs the studio from the terminal: ./skill.sh --dispatch-master <objective.md>. It carries the same ideas — a 4-tier chain of command (General Manager → Store → Shift → Crew), a HITL Deep-Sleep gate, a continuity engine, self-healing, an append-only memory/audit.jsonl, and real on-disk deliverables. lib/minimax.sh bridges the shell orchestrator to real MiniMax-M3; with no key it falls back to a deterministic stub.

Configuration & the mock guard

One source of truth for the model, endpoint, and key — plus a preflight that refuses to run silently on the mock.

The model, endpoint, and key come from one place: the environment (.env or exported vars), read identically by the Python engine and the bash skills. There is no scattered llm_config.json; nothing is duplicated across files, so there are no precedence conflicts. The JSON files are engine-specific: config/weights.json and config.json belong to the Python engine, config.minimax.json to the v3 CLI skill.

The one real footgun is the silent mock: with no key (or a wrong base URL) the client falls back to a deterministic offline mock so demos never crash — which in production means you can run on the mock without noticing. scripts/preflight.py closes that hole: it validates the environment, parses every config file, and sends one tiny real request to confirm you are authenticated on live MiniMax-M3. It fails loudly (and --require-live exits non-zero for CI) instead of mocking silently.

python scripts/preflight.py            # human-readable report
python scripts/preflight.py --require-live   # non-zero unless live M3

Feedback & learning (the glass box)

How human corrections retrain the Expectimax weights — where they persist, and the exact math of one override.

An operator override is appended to supervisor_data/feedback.json; the run_training tool runs FeedbackTrainer; update_weights() applies the result in memory, persists it to config/weights.json (so it survives a restart and is version-controlled), and appends a timestamped row to supervisor_data/weight_history.jsonl. scripts/plot_weight_drift.py charts that history so accumulating operator bias is visible, not hidden.

The rule is a slow perceptron step, learning rate 0.01: W_new = W_old + 0.01 × (H_correct − H_incorrect), then normalized to sum 1 and clamped ≥ 0. Each heuristic is in [0,1], so one override moves a weight by at most 0.01 — about five consistent overrides to shift a weight ~0.05. (The hard 0.4 / 0.9 action gates are fixed in code; overrides retrain the utility weights, not those gates.)

reference

Architecture

A four-tier chain of command that isolates context per tier and eliminates drift.

T0
General ManagerReceives the master objective, performs deep decomposition, owns the plan.
T1
Store SupervisorDomain strategy — routes to the right specialist swarm, allocates resources.
T2
Shift SupervisorTactical QA — spawns workers, enforces continuity, holds the HITL checkpoint.
T3
The CrewSpecialist workers — generate the deliverable; never see outside their scope.

In the Python engine these map to Orchestrator (T0/T1 planning & routing), SupervisorCore + the M3 audit (T2 verification & HITL), and the roster personas (T3 workers). The whole thing pivots on one class — LLMClient — so retargeting the model is a single-file change.

Glossary

Key terms, quickly.

DAG
The task graph M3 plans; a task runs only when its dependencies pass.
Audit
M3’s verdict on whether an output satisfies its plan + continuity.
Drift
An output wandering from the goal; caught by the coherence check & audit.
HITL
Human-in-the-loop — the approval gate on high-stakes tasks.
Deliverable
A verified worker output written to disk as a real file.
Persona
A specialist agent’s system prompt, from the roster.
Synthesis
The final verified result, assembled once all deps pass.
Mock fallback
Deterministic offline behavior when no key is set.
