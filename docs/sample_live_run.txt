## 1. Bug analysis (static)

`billing/discount.py` defines:

```python
def apply_discount(price, percent):
    return price - (price * percent / 100)
```

Two defects, both reproducible by inspecting the expression algebraically:

| Defect | Trigger | Expression evaluated | Returned value | Why it's wrong |
|---|---|---|---|---|
| Negative price on over‑discount | `apply_discount(100, 150)` | `100 - (100 * 
150 / 100)` = `100 - 150.0` | `-50.0` | A monetary price cannot be negative; the
identity only yields a valid price for `percent ∈ [0, 100]`. |
| `TypeError` on `None` percent | `apply_discount(100, None)` | `100 * None` | 
raises `TypeError` | `None` cannot participate in numeric arithmetic. |

Expected contract after the fix:

- `percent` is treated as `0` when it is `None`.
- `percent` is clamped into `[0, 100]` before the arithmetic: `> 100` becomes 
`100` (full discount, price → `0` for `price ≥ 0`); `< 0` becomes `0` (no 
discount).

**Full corrected file:**

```python
def apply_discount(price, percent):
    # Treat a missing percent as 0 (no discount).
    if percent is None:
        percent = 0
    # Clamp percent to the valid range [0, 100] so the result is never negative.
    percent = min(max(percent, 0), 100)
    return price - (price * percent / 100)
```

### Rationale (defended by code, not by execution)

1. The `is None` check must come **before** any numeric operation. `max(percent,
0)` and `min(...)` on `None` raise `TypeError`, so order matters: first coerce 
`None → 0`, then clamp.
2. The clamp `min(max(percent, 0), 100)` is the standard idiom for "clamp to 
`[lo, hi]`" and produces the exact values required by the contract: `< 0` → `0`,
`> 100` → `100`, in‑range unchanged.
3. The arithmetic is unchanged, so for any in‑range `percent` the function's 
output is bit‑identical to the original (modulo Python's normal `int/int → 
float` division).
4. Out of scope: `price` validation and non‑numeric `percent` (e.g. strings) — 
issue #482 explicitly scopes the fix to the `percent` argument, and these would 
already raise `TypeError` from the original arithmetic, so the fix does not 
regress them.
